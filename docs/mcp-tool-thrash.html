MCP Tool Thrash (hidden agent fault for Agent Observability Signals)

A demo fault that makes every chat turn thrash between tool calls on a synthetic MCP server — a loop of redundant lookup → refine → lookup → refine … calls that never converges on an answer. The behavior is hidden from the chat user (the answer text and the visible pipeline stages are unchanged) and is designed to be detected by Splunk Agent Observability Signals, the LLM that mines an agent stream's traces for recurring failure patterns.

It ships as a server-side Demo Controls toggle, MCP Tool Thrash, in the Agent Pipeline group — off by default.

Why it reads as a failure to Signals

Signals mines the LLM reasoning and agent-decision spans for recurring failures — a silent row of successful tool calls next to a correct answer is not one. So the thrash is rebuilt as an agent failing to converge: each tool call is preceded by a scripted mcp_reasoning LLM span that narrates the floundering ("still conflicting — re-running the lookup, again"), and the mcp_tool_broker agent span ends status 500 with a give-up output ("going in circles … abandoning the lookup without a result"). The reasoning is scripted (no real model call) and the chat answer is untouched, so the behavior stays hidden from the user while the trace shows the tool-loop failure Signals clusters on.

How it works

The thrash rides the shared guardrail chain so both blueprint cores (pseudoco_multi_agent, nvidia_virtual_assistant) get it identically — no core changes (backend/agents/blueprints/guardrails.py):

1. mcp_thrash_launch (last PRE node) — if the toggle is on and the theme has a profile, it spawns a daemon thread that drives the scripted loop against the in-process SyntheticMcpServer and returns immediately. The thread overlaps the synthesizer's 30–40 s LLM call, so the thrash adds no user-visible latency. 2. mcp_thrash_join (POST node, just before governance) — joins the thread (bounded) and writes the collected records to state["tool_thrash_trace"]. 3. governance_node carries the records onto the turn's governance event (tool_thrash), exactly as it carries agent_control_verdicts. 4. agent_observability._add_tool_spans rebuilds them as an abandoned mcp_tool_broker agent span wrapping the alternating mcp_reasoning LLM → tool loop (see "Why it reads as a failure to Signals") on the turn's chat_turn trace — in the theme's own Agent stream, where Signals runs.

Neither thrash node is terminal and neither has a label in frontend/js/chat.js STAGE_LABELS, so the SSE stage frame they emit changes nothing the user sees ("Unknown nodes keep the previous label").

Why the SDK-rebuild path, not live execute_tool spans

The tool spans are rebuilt afterward from the governance event (the agent_control_verdicts precedent), not emitted as live otel.tool_span execute_tool spans during the turn. That keeps them:

  • in the per-theme Agent stream and inside the same trace as the real turn (the collector overlay would pin raw execute_tool spans to the single default stream and a different trace id), and
  • out of the OTel collector and Splunk APM entirely — so no execute_tool dashboard or detector is polluted and there is no double-count.

Per-theme verticalization

Each theme carries its own McpThrashProfile on ThemeConfig.thrash (backend/services/mcp_thrash.py), like SchedulingProfile — its own synthetic server name, entity and tool set, so the thrash reads like that vertical's own agent fumbling its backend. A theme that defines none falls back to DEFAULT_THRASH; never branch on the theme key in the nodes.

The toggle

  • Server-side, persisted (settings_store mcp_tool_thrash), like NemoClaw Guardrails: it applies to every chat turn from every client, and the posture survives a restart.
  • Turn it on from the chat page's Demo Controls → Agent Pipeline → MCP Tool Thrash, or PUT /api/settings/mcp-thrash {"enabled": true}.
  • Hiding the card from the Settings panel does not stop it (server-side toggles keep running while hidden) — the toggle is the only off switch.
